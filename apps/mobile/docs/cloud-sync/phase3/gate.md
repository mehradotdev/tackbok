Date: 2026-08-09

Status: **CONDITIONALLY CLOSED — Phase 4 may begin under the owner waiver in
[`waiver.md`](./waiver.md).**

The Google Drive adapter and authorization code are implemented. Every
account-independent check is green, and the owner's probe passes executed the
account and Drive obligations against real Google Drive with disposable test
accounts. Five of the seven merge-blocking probes are closed on evidence; the

All evidence comes from an emulator and a simulator. No physical device was
available; the waiver records that, what it costs, and what is owed on the first

## Account-independent evidence

- [x] `bun run phase3:test`: **2 suites passed, 10 tests passed, 0 failed**.
- [x] Immutable writes tolerate a same-content duplicate and reject a same-key,
  different-content collision under the mocked Drive API.
- [x] Downloads are stream-hashed and reject corrupt bytes; a 401 clears the
  cached access token and retries authorization once.
- [x] Resumable uploads use 256 KiB boundaries, replace expired sessions, persist
  session URI/expiry in `sync_remote_objects`, query Drive's accepted offset after
  restart, and continue from that offset.
- [x] Persisted resumable-session URLs are accepted only for the exact
  `https://www.googleapis.com` origin; a malicious SQLite URL is discarded and
  never receives a request or bearer token.
- [x] Large downloads resume into a durable sink with an HTTP byte range, avoid
  whole-file buffering in the adapter, and verify the completed SHA-256 before
  returning the object as trusted.
- [x] Mocked permanent deletion is idempotent, and a bounded vault purge removes
  ordinary objects while preserving `revocations/` markers.
- [x] Disconnect performs local token/session cleanup without calling Google's
  global revocation endpoint or issuing a Drive request.
- [x] OAuth token storage is isolated to `expo-secure-store`; SQLite, Zustand,
  diagnostics, and logs receive no tokens.
- [x] Account emails are reduced to a masked, in-memory cosmetic label. The
  reserved `cloud_vault.account_label` column remains null and is not a storage
  destination.
- [x] iOS clears SecureStore credentials only for terminal refresh failures
  (`invalid_grant`/401); transient network and server failures retain the
  refresh token for retry.
- [x] Android inline Google Authorization module compiles:
  `:app:compileDebugKotlin` → **BUILD SUCCESSFUL**.
- [x] iOS authorization/native-module integration compiles in an arm64 Debug
  simulator build → **BUILD SUCCEEDED**.
- [x] `bun run typecheck` passes.

The two compile results are integration smoke evidence only. They are not
release-signed or physical-device evidence.

## Owner probe evidence — 2026-08-09

Two full automatic passes were run against real Google Drive using disposable
test accounts (a separate account per platform, so neither run could disturb the
other's `appDataFolder`). Reports are in [`evidence/`](./evidence/); both are
recorded verbatim as the harness wrote them.

| | Android | iOS |
|---|---|---|
| runtime | emulator, API 36, debug | simulator, iOS 26.5, debug |
| vault | `probe-mslob1c3` | `probe-mslp3nk2` |
| overall | `skipped` (only `session.natural-expiry`) | `skipped` (only `session.natural-expiry`) |
| failed / inconclusive steps | 0 | 0 |

Both passes used the 200 MiB fixture and produced the **same SHA-256**
(`502bfded…3868`) from independently generated bytes, which is cross-platform
evidence for the frozen Phase-0 fixture generator as well.

A later pass on 2026-08-09 covered the external-revocation and Disconnect legs
against a grant revoked for real in Google account settings. iOS passed every
one. Both platforms detected the revocation itself correctly and differed
exactly as the auth policy says they should: Android surfaced `provider:auth`
and retained credentials for retry, iOS surfaced `auth:refresh-failed` and
discarded them, because a revoked grant is a terminal refresh failure.

Android produced two findings, and the first of them corrects an earlier
conclusion recorded here:

- **Recovery works, after a delay.** Reconnect was a silent no-op for roughly
  half an hour after revocation — no consent screen, cached revoked token,
  success reported — and then recovered normally once Play services noticed.
  This was first written up as a permanent failure on the strength of a
  27-minute observation window; that was an overreach and is corrected in
  [findings/0001](./findings/0001-android-revocation-recovery.md). The residual
  defect is that the app reports success while doing nothing.
- **Disconnect does not disconnect** *(fixed the same day)*. The next Drive
  write after a local Disconnect succeeded, because Android lacked the iOS
  check that treats absent stored credentials as `not-connected`, and Play
  services still holds the grant. A two-account test showed the interactive
  path shared the defect: reconnect silently reattached the previously granted
  account with no chooser. Fixed with a durable connection mark, the device
  account chooser on every interactive connect, and account pinning for silent
  renewals; re-verified on-device the same day, including a full quick-fixture
  regression pass. See
  [findings/0002](./findings/0002-android-disconnect-does-not-disconnect.md).

Findings that distinguish the two platforms:

- **Android renews without a refresh credential**
  (`hadRefreshCredentialBefore: false`): Play services mints access tokens
  directly. **iOS renews from a stored refresh token**
  (`hadRefreshCredentialBefore: true`). This is the split the two E2E gate items
  exist to separate, and each platform answered its own half.
- Resume arithmetic is identical and exact on both: interrupted at 83,886,080
  bytes, resumed with 482 requests of which **480 were HTTP 308** — precisely
  the 120 MiB remainder at the 256 KiB chunk boundary. Download resumed from
  62,914,560 bytes with a single HTTP 206 and a matching SHA-256.
- Upload throughput differed by runtime (0.37 vs 0.89 MiB/s) and download did
  not (21.35 vs 21.94 MiB/s). Neither figure is device performance; every
  transfer fact carries `runtime: emulator-or-simulator`.

What the passes cover, and what they do not:

- **Fully covered:** interactive consent on a disposable account; ADR 0003
  items 1, 2, 3, 5 and 6; the interrupted revocation purge (9 sweeps, 13 objects
  deleted, both revocation kinds surviving, zero non-markers left); the 200 MiB
  fixture round trip; silent/refresh renewal on both platforms.
- **Partially covered:** ADR 0003 item 4. Drive answered a dead session URI with
  a real 404 and the adapter restarted the upload, but expiry was forced rather
  than awaited. `session.natural-expiry` is recorded `skipped` on both runs.
- **Covered by the later revocation pass:** external authorization failure and
  recovery, and local Disconnect, on both platforms. iOS passed all of them;
  Android passed everything except Disconnect.
- **Not covered by any pass:** release-signed builds, which are an EAS artifact
  rather than a probe. Both runtimes are emulated, so no physical-device item is
  satisfied.

## Security rules during the probes

Use only disposable test data. Evidence must contain no access/refresh token,
account email or stable account identifier, journal text, media bytes, or Drive
session URI. Disconnect must remain local sign-out only and must never call
Google's global revocation endpoint.
