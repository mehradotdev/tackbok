# Finding 0001: protocol-v2 large media crosses a whole-buffer boundary

Status: **OPEN — blocks Bundle b1 acceptance, c1, and c2**
Observed: 2026-08-15
Evidence class: Android API-36 emulator, Debug build

## Reproduction

The synthetic fixture was generated by the V7-5 tool, transferred through the
ordinary Android Files path, and accepted only after its frozen 200 MiB size
and SHA-256 matched. The probe stored the normalized media row with a null hash
and size. The production native streaming hasher filled both fields, and the
durable probe verified the file and recorded production values in 265 ms.

The following publication then failed before a resumable upload could begin.
Android reported failed allocations of 209,715,212 and 209,715,216 bytes with a
201,326,592-byte managed-heap growth limit. Emulator process RSS sampled around
1.0–1.1 GiB during the failed attempt. These are emulator observations, not
physical-device performance claims.

The local journal generation remained queued after the failure and after a
force-stop/relaunch. No local journal row or media file was lost. The runtime
retried on launch and reached the same allocation failure, so the defect is a
liveness and memory-safety failure rather than demonstrated data loss.

The finalized redacted scenario report is
[`evidence/2026-08-15-android-emulator.json`](../evidence/2026-08-15-android-emulator.json).

## Cause

The hash path is streaming, but the transfer contract is not:

- `ProductionSnapshotV2MediaStore.readVerified()` calls `File.bytes()` and
  returns one `Uint8Array`;
- `SnapshotV2Provider.uploadMedia()` accepts that whole array;
- the Drive resumable uploader slices chunks only after the complete array is
  already resident; and
- the reverse path collects all response chunks and concatenates them before
  staging and verification.

The probe preparation also used `File.copy()` for an external Android content
URI. It was changed during this round to the native `copyAsync()` relocation
path with document-picker cache copying disabled, so fixture preparation no
longer introduces a second whole-file allocation. That correction does not
hide or fix the production transfer failure above.

## Required remediation

Reopen the v2 media transfer design while retaining the reviewed v1 streaming
implementation as a reference. Acceptance requires bounded upload and download
sources/sinks end to end: file-backed resumable chunks, durable resume offsets,
temporary-file download, native streaming hash verification, atomic promotion,
and regression tests proving no whole-media `Uint8Array` is required. Then
repeat the b1 upload/interruption/restore/Wi-Fi scenarios with the same frozen
fixture. Do not proceed to v1 purge or retirement before owner review accepts
that rerun.
