## Blocking

### B1 — the checkpoint is super-quadratic in vault size

`InMemorySyncDevice.toDurableSnapshot()` serializes the **entire** engine —
`domain`, every `VersionGraph`, `outbox`, `appliedHeads`, `conflicts`,
`seedItems`, the staged change page — and `checkpoint()` is invoked on every
mutation, every pulled page, every apply, every publish step, every purge
batch, and every settle. Each of those calls stringifies the whole state and
rewrites one SQLite row.

Measured, on this machine, seeding a fresh vault of ~400-character entries
through `SQLiteSyncEngine` with the real migration and a real SQLite database:

| entities | passes | checkpoint row | checkpoint saves | JSON written | wall clock |
| --- | --- | --- | --- | --- | --- |
| 500 | 11 | 1.3 MB | 4,783 | 4.99 GB | 4.7 s |
| 2,000 | 41 | 5.0 MB | 49,123 | 204.49 GB | 186.2 s |

Growth between those two points is ≈ n^2.7; quadratic is the floor, because
snapshot size is O(n) and the number of saves is itself O(n). 2,000 entries is
about five and a half years of daily journaling — not an edge case — and it
costs three minutes of pure CPU on a fast desktop before any network work.

Against the §13 targets (20,000–50,000 entity-version files, peak JS heap
≤ 250 MB, full text restore ≤ 30 min on a mid-tier 2022 Android):

- at the quadratic floor, 50,000 entities is 625× the 2,000-entity row —
  ~128 TB of JSON serialization and ~32 hours of CPU;
- the single `snapshot_json` row reaches ~125 MB, held simultaneously as a JS
  string, a parsed object graph, and a SQLite TEXT value — over the whole
  restore heap budget before anything else is allocated.

The right design is already written down in the code. `src/db/schema.ts:296`
says of `sync_engine_checkpoints`: *"The normalized/domain and protocol tables
remain authoritative; this row keeps the pass-local cursor, staged page, seed
cursor, and purge cursor together so a process death cannot create a mixed
checkpoint."* That is correct and it is not what the code does — restore reads
exclusively from the blob and the Phase-1 tables are a write-only mirror. Make
the code match the comment: rehydrate `domain`, `generations`, `graphs`,
`outbox`, `appliedHeads` and `conflicts` from `syncVersions`,
`syncEntityState`, `syncConflicts`, `syncChangeQueue` and the normalized domain
tables — which exist for exactly this and are already being written — and keep
only the small pass-local state in the checkpoint row.

### B2 — the 34-scenario catalog never exercises the restore path

`phase4-gate.test.ts` runs each frozen scenario with `SQLiteSyncEngine` as the
device factory, but every scenario constructs each device exactly once, and the
per-device checkpoint store is empty at construction. `store.load()` therefore
returns `null` in all 34 scenarios and `restoreDurableSnapshot()` is never
called.

What the catalog run proves is that *writing* a checkpoint at every step does
not perturb the frozen semantics. That is worth having. It is not the Phase-2
carried obligation, which is durable **restart** from the production engine.
Restore fidelity is currently covered only by the hand-written restart tests —
a handful of single-entity cases against one entity id.

The gate's first ticked item should not read as if the catalog were re-proven
across restart. Fix the coverage rather than the wording: wrap the factory so
each device is torn down and reconstructed from SQLite between operations. The
chaos test already does this (`devices = ['a','b','c'].map(open)` between
passes); the same trick applied to the catalog runner is cheap and is the
single highest-value test in this phase.

### B3 — initial seeding materializes the whole journal, twice

`ProductionRuntimeEngine.sync()` calls `enumerateNormalizedDomain()`, which
loads every entity's full state into memory, and hands the whole array to
`engine.seed()`, which retains it in `seedItems` — and therefore re-serializes
it into the checkpoint row on every subsequent checkpoint until seeding drains.
For the user this design is aimed at, the first sync loads the entire journal
into JS memory and writes it to SQLite tens of thousands of times.

Seeding should be a cursor over the normalized tables (`id > cursor LIMIT
batch`), not a materialized list. The existing `seedCursor` already provides the
resume point.

## Should fix before 4b

- **S1 — nothing triggers a sync when the user saves.** Implemented triggers
  are app-active, connectivity-restored, backgrounding and the periodic task.
  §9 wants network work "debounced ~30–120 s so bursts become one version",
  which presupposes an edit-driven trigger. As written, an entry written while
  the app stays foregrounded waits for the user to background the app — or for
  an OS periodic wake that iOS may defer for hours. 4b's **Sync now** button
  will paper over this in testing; real usage will not.
- **S2 — triggers arriving during a pass are dropped.**
  `SyncRuntime.run()` returns the in-flight promise instead of queueing a
  follow-up pass. The in-flight pass hydrated its outbox at the start, so an
  edit committed mid-pass is neither included nor rescheduled.
- **S3 — the entire React Query cache is invalidated after every pass.**
  `ProductionRuntimeEngine` awaits `onRemoteApplied?.()` unconditionally;
  `_layout.tsx` maps it to `queryClient.invalidateQueries()`. §13 asks for
  invalidation *on remote apply* — gate it on `result.applied > 0`.
- **S4 — the background task is registered for every user.** `_layout.tsx`
  calls `registerCloudSyncBackgroundTask()` on every launch regardless of
  whether a vault is configured, so users who never connect Drive get a
  15-minute OS wake that does nothing. Gate it on a configured vault (and later
  on the Phase-5 feature flag).
- **S5 — per-pass writes are O(whole vault).**
  `persistProductionEngineResult()` upserts every version of every graph on
  every pass, and `materializeProductionDomain()` rewrites every applied entity
  on every pass. Same root cause as B1; both should be driven by what changed
  in the pass.

## Minor

- `VersionGraph.restoreDurableState()` falls back to `splice(0, 1)` when no
  pending version has its parents satisfied, so a corrupt snapshot yields a
  silently incomplete graph instead of throwing.
- `failureCategory()` cannot produce the declared `'offline'` category — it is
  in the type and unreachable in the code.
- `_layout.tsx`'s start/stop effect leaks the first `start()`'s listeners under
  React's dev double-invoke: `stop()` clears `subscriptions` before the still-
  awaiting `start()` assigns them.

## Confirmed good

These were checked specifically because they are the standing constraints, and
they hold:

- `createProductionRuntimeEngine()` is the sole runtime construction path and
  builds `GoogleDriveProvider({ auth: createGoogleAuthorization() })`, so
  Android token minting stays behind `AndroidGoogleAuthorization` and its
  durable connection mark. No global OAuth revocation endpoint was added and
  Disconnect is untouched.
- Analytics payloads are buckets and enums only — no token, account label,
  entity id, hash, filename, URI, or journal field is reachable from them.
- No notification-permission dependency, asserted by a source scan over the
  runtime modules and `_layout.tsx`.
- Media never enters JS memory whole: production registers 1 MiB-chunked file
  sources through `registerBlobSource`, and `persistInlineBlobs` — the only
  path that puts bytes in the checkpoint — is gate-only.
- Both byte-removal paths (entry asset replacement, profile-photo replacement)
  write the retained-media ledger and a completed obligation inside the same
  transaction as the delete.
- `shouldAdoptQueuedGeneration()` correctly handles the crash gap between the
  engine checkpoint and Phase-1 queue settlement, and is directly tested.
- The readiness gate is real: the engine is not constructed until
  `isNormalizedModelReady()` is true, and the launch-only backfill was replaced
  by an in-session retry timer. This satisfies the merge-blocking §12
  obligation.

## Implementation response — Phase 4a.1 — 2026-08-10 05:12 IST

pass. It consumes a touched-key set populated by remote pulls, local captures,
CAS retries, and late dependency/recovery arrivals. Cross-entity recoveries use
an incremental reverse-dependency index; restoration rebuilds that index once
and derives any graph whose complete heads differ from its applied heads. A new
restart regression proves that an incomplete resolution is not dropped when
its recovery arrives in a later pass. Degraded keys remain retryable: a bad
object touches and records the entity, and a later valid object clears the
degraded marker and touches it again.

Two corrections to my own review record:

- I attributed part of the baseline to `FakeCloudProvider.getChanges()`, which
  does a `filter().sort()` over all objects per page. That scan is real, but
  measured against the raw provider the sync-only figures are 0.8 s / 1.7 s —

- The touched-key resolve loop I asked for accounts for only about 11% of the
  gain (7,600 → 6,768 ms at 10,000). The dominant defect was the redundant
  per-entity `UPDATE sync_versions ... WHERE vault_id = ?`, which SQLite served
  from the vault-only index, found and removed during 4a.1 (6,768 → 610 ms).
  Credit for that belongs to the implementation, not to this review.

The removed `UPDATE` is safe: `VersionGraph` never deletes versions, so the
graph delta always carries the complete version set and each upsert writes its
own exact `applied` bit. There is no row the removed statement could have
cleared that the upserts do not now cover.

The touched-key set is complete. Every `graph.add()` site either enqueues its
key or is followed directly by `applyVersion`; deferred keys are skipped
*before* the delete, so they survive to a later pass; and because `heads()`
returns only complete versions, a late recovery changes the head set, which is
exactly what restoration's heads-vs-applied comparison detects. The one gap I
found — recovery keys are not re-enqueued when their parent item is skipped by
CAS — self-heals on the next pass, since `resolveHeads` re-derives recoveries,
and on restart via the same comparison.

### Should fix before the gate closes

- **F1 — the Danger Zone rewrite reaches outside the cloud feature and weakens
  the app's most destructive warning.** `DangerZoneSection` is not a cloud
  surface, but 4b renames *Delete All Data* to *Reset this device only*, changes
  its description to "Disconnect, then delete local journal data only", and
  replaces the confirmation body "This action cannot be undone. All your app
  data will be permanently deleted." with "This device disconnects first, then
  deletes its local journal. The cloud backup and other devices remain."

  For every user who has not connected Drive — which is all of them until this
  ships, and most of them after — there is no other device and no cloud copy, so
  the new copy is simultaneously meaningless and *less* alarming than the truth:
  "only" and "local journal data only" read as a partial reset, and the
  irreversibility sentence is gone. The row also now routes through
  `resetThisDeviceOnly()`, which calls `signOut()` and
  `setCloudSyncBackgroundTaskEnabled(false)` unconditionally for users who never
  connected anything.

  Keep the original label and the "cannot be undone" sentence when
  `!snapshot.configured`, and use the cloud-aware copy only when a vault exists.

  Related, and correct but worth recording: the `retainedMediaForSync` guard is
  gone, so photos and voice memos are now always deleted here. That is
  consistent, because `clearLocalCloudReplica()` drops
  `sync_retained_media` and `sync_media_obligations` in the same action — but it
  is a silent behaviour change to a pre-4b path and is not mentioned in the gate.

- **F2 — an expired Drive list-page token strands a restore permanently.** The
  new compound cursor `tackbok-initial-restore:{startPageToken,listPageToken}`
  is persisted in the engine checkpoint by `checkpoint('pull-page')`. A Drive
  `files.list` page token is not durable; after process death and a long enough
  gap Drive rejects it. `statusError()` turns that into `transient` (or
  `not-found` for 404/410), `pullAllChanges()` throws before reaching line 823,
  so `this.cursor` is never rewound, and every later pass replays the identical
  failing request. The user sees a generic sync failure forever, with no
  recovery short of Disconnect and reconnect. `grep` confirms no cursor-reset
  path exists in `engine/` or `runtime/`.

  The fix is cheap because `startPageToken` is already inside the cursor: on a
  `corrupt` or `not-found` failure for the list half, drop `listPageToken` and
  restart the listing from the beginning. Re-listing is idempotent — entity
  version files are immutable and hash-addressed.

- **F3 — initial restore fans out a whole Drive page in parallel, and a 403 is
  reported as an auth failure.** `getInitialRestorePage()` does `Promise.all`
  over every `entities/` file in a list page, so with the production
  `pageSize` default of 100 a restoring device issues up to 100 concurrent
  authenticated downloads. `request()` retries three times with no backoff and
  never honours `Retry-After`. `statusError()` maps **403 to `auth`**, so
  Drive's `userRateLimitExceeded` — a 403 — is not retried and surfaces to the
  user as an authorization problem, prompting them to reconnect an account that
  is working fine. The mapping is pre-existing Phase-3 code; 4b is the first
  path that makes it likely. Bound the concurrency and separate rate-limit 403s
  from genuine auth 403s.

### Minor

- **F5 — restoring from Drive during onboarding skips the rest of onboarding.**
  `handleComplete()` sets `hasCompletedOnboarding` and `router.replace('/')`, so
  a restoring user never reaches the privacy/analytics consent step or theme and
  font setup. Defensible, since analytics default to off and a restore implies a
  returning user — but it is an undocumented change to the onboarding flow and
  the gate does not mention it.
- **F6 — crash window between the journal wipe and the replica clear.**
  `resetThisDeviceOnly()` runs `deleteAllData()` and `clearLocalCloudReplica()`
  as separate transactions. If the process dies between them, `sync_change_queue`
  holds a delete for every entity while `cloud_vault.status` is `'disabled'`.
  Nothing runs today, because `createProductionRuntimeEngine()` will not build
  for a disabled vault — but if the user later reconnects that same vault, those
  queued deletions publish and destroy the cloud copy, the exact opposite of
  "the cloud backup and other devices remain". Clear the queue inside the wipe
  transaction, or gate outbox hydration on a vault generation.
- **F7 — the 4b gate's evidence is string matching.** `phase4b-gate.test.ts` is
  six tests of the shape `expect(source).toContain('accessibilityLiveRegion=
  "polite"')`. That is a useful drift alarm and worth keeping, but it proves a
  token appears somewhere in a file, not that the status region is labelled or
  that the flow behaves. The accessibility bullet should say "source-contract
  checks" rather than "requirements have host-verifiable coverage". The
  Host-only boundary section below it is honest and correctly names what was not
  exercised.
- `disconnectGoogleDrive()` issues `db.update(cloudVault).set(…)` with no
  `.where()` — the same device-blind shape as N6. Correct today; worth a comment.
- `revokeCloudVault()` wraps a single `eq()` in `and()`.

### Confirmed good

- `stop()` now nulls `this.engine`, and the gate test proves two `start()` calls
  build two engines. Combined with the 4a.1 vault-switch teardown in `load()`,
  Disconnect → connect to a different vault cannot retain the prior attachment.
- The initial-restore compound cursor is genuinely restartable within a process,
  and `pullAllChanges()` still advances the cursor only after a page is fully
  consumed, so the 500-entity cap cannot skip a tail.
- `hasPendingWork()` cannot spin: a pass returns early only after admitting 500
  distinct entities, so each rerun makes bounded forward progress, and a failed
  pass does not set `rerunTrigger`. Background passes pass `allowFollowup:
  false` and stay bounded.
- Wi-Fi-only media gates hashing and blob registration, not text sync.
- `journal-deleted` wipes through `wipeProductionJournalAfterRevocation()`
  without touching the routed write paths, so it creates no outbox intent.
- The settings store migration is a real `version: 1` zustand migration that
  strips both legacy fields and defaults `cloudSyncWifiOnlyMedia` to `true`.
