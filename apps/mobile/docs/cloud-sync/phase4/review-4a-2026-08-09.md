## Blocking

### B1 — the checkpoint is super-quadratic in vault size

`InMemorySyncDevice.toDurableSnapshot()` serializes the **entire** engine —
`domain`, every `VersionGraph`, `outbox`, `appliedHeads`, `conflicts`,
`seedItems`, the staged change page — and `checkpoint()` is invoked on every
mutation, every pulled page, every apply, every publish step, every purge
batch, and every settle. Each of those calls stringifies the whole state and
rewrites one SQLite row.

Measured, on this machine, seeding a fresh vault of ~400-character entries
through `SQLiteSyncEngine` with the real migration and a real SQLite database:

| entities | passes | checkpoint row | checkpoint saves | JSON written | wall clock |
| --- | --- | --- | --- | --- | --- |
| 500 | 11 | 1.3 MB | 4,783 | 4.99 GB | 4.7 s |
| 2,000 | 41 | 5.0 MB | 49,123 | 204.49 GB | 186.2 s |

Growth between those two points is ≈ n^2.7; quadratic is the floor, because
snapshot size is O(n) and the number of saves is itself O(n). 2,000 entries is
about five and a half years of daily journaling — not an edge case — and it
costs three minutes of pure CPU on a fast desktop before any network work.

Against the §13 targets (20,000–50,000 entity-version files, peak JS heap
≤ 250 MB, full text restore ≤ 30 min on a mid-tier 2022 Android):

- at the quadratic floor, 50,000 entities is 625× the 2,000-entity row —
  ~128 TB of JSON serialization and ~32 hours of CPU;
- the single `snapshot_json` row reaches ~125 MB, held simultaneously as a JS
  string, a parsed object graph, and a SQLite TEXT value — over the whole
  restore heap budget before anything else is allocated.

The right design is already written down in the code. `src/db/schema.ts:296`
says of `sync_engine_checkpoints`: *"The normalized/domain and protocol tables
remain authoritative; this row keeps the pass-local cursor, staged page, seed
cursor, and purge cursor together so a process death cannot create a mixed
checkpoint."* That is correct and it is not what the code does — restore reads
exclusively from the blob and the Phase-1 tables are a write-only mirror. Make
the code match the comment: rehydrate `domain`, `generations`, `graphs`,
`outbox`, `appliedHeads` and `conflicts` from `syncVersions`,
`syncEntityState`, `syncConflicts`, `syncChangeQueue` and the normalized domain
tables — which exist for exactly this and are already being written — and keep
only the small pass-local state in the checkpoint row.

### B2 — the 34-scenario catalog never exercises the restore path

`phase4-gate.test.ts` runs each frozen scenario with `SQLiteSyncEngine` as the
device factory, but every scenario constructs each device exactly once, and the
per-device checkpoint store is empty at construction. `store.load()` therefore
returns `null` in all 34 scenarios and `restoreDurableSnapshot()` is never
called.

What the catalog run proves is that *writing* a checkpoint at every step does
not perturb the frozen semantics. That is worth having. It is not the Phase-2
carried obligation, which is durable **restart** from the production engine.
Restore fidelity is currently covered only by the hand-written restart tests —
a handful of single-entity cases against one entity id.

The gate's first ticked item should not read as if the catalog were re-proven
across restart. Fix the coverage rather than the wording: wrap the factory so
each device is torn down and reconstructed from SQLite between operations. The
chaos test already does this (`devices = ['a','b','c'].map(open)` between
passes); the same trick applied to the catalog runner is cheap and is the
single highest-value test in this phase.

### B3 — initial seeding materializes the whole journal, twice

`ProductionRuntimeEngine.sync()` calls `enumerateNormalizedDomain()`, which
loads every entity's full state into memory, and hands the whole array to
`engine.seed()`, which retains it in `seedItems` — and therefore re-serializes
it into the checkpoint row on every subsequent checkpoint until seeding drains.
For the user this design is aimed at, the first sync loads the entire journal
into JS memory and writes it to SQLite tens of thousands of times.

Seeding should be a cursor over the normalized tables (`id > cursor LIMIT
batch`), not a materialized list. The existing `seedCursor` already provides the
resume point.

## Should fix before 4b

- **S1 — nothing triggers a sync when the user saves.** Implemented triggers
  are app-active, connectivity-restored, backgrounding and the periodic task.
  §9 wants network work "debounced ~30–120 s so bursts become one version",
  which presupposes an edit-driven trigger. As written, an entry written while
  the app stays foregrounded waits for the user to background the app — or for
  an OS periodic wake that iOS may defer for hours. 4b's **Sync now** button
  will paper over this in testing; real usage will not.
- **S2 — triggers arriving during a pass are dropped.**
  `SyncRuntime.run()` returns the in-flight promise instead of queueing a
  follow-up pass. The in-flight pass hydrated its outbox at the start, so an
  edit committed mid-pass is neither included nor rescheduled.
- **S3 — the entire React Query cache is invalidated after every pass.**
  `ProductionRuntimeEngine` awaits `onRemoteApplied?.()` unconditionally;
  `_layout.tsx` maps it to `queryClient.invalidateQueries()`. §13 asks for
  invalidation *on remote apply* — gate it on `result.applied > 0`.
- **S4 — the background task is registered for every user.** `_layout.tsx`
  calls `registerCloudSyncBackgroundTask()` on every launch regardless of
  whether a vault is configured, so users who never connect Drive get a
  15-minute OS wake that does nothing. Gate it on a configured vault (and later
  on the Phase-5 feature flag).
- **S5 — per-pass writes are O(whole vault).**
  `persistProductionEngineResult()` upserts every version of every graph on
  every pass, and `materializeProductionDomain()` rewrites every applied entity
  on every pass. Same root cause as B1; both should be driven by what changed
  in the pass.

## Minor

- `VersionGraph.restoreDurableState()` falls back to `splice(0, 1)` when no
  pending version has its parents satisfied, so a corrupt snapshot yields a
  silently incomplete graph instead of throwing.
- `failureCategory()` cannot produce the declared `'offline'` category — it is
  in the type and unreachable in the code.
- `_layout.tsx`'s start/stop effect leaks the first `start()`'s listeners under
  React's dev double-invoke: `stop()` clears `subscriptions` before the still-
  awaiting `start()` assigns them.

## Confirmed good

These were checked specifically because they are the standing constraints, and
they hold:

- `createProductionRuntimeEngine()` is the sole runtime construction path and
  builds `GoogleDriveProvider({ auth: createGoogleAuthorization() })`, so
  Android token minting stays behind `AndroidGoogleAuthorization` and its
  durable connection mark. No global OAuth revocation endpoint was added and
  Disconnect is untouched.
- Analytics payloads are buckets and enums only — no token, account label,
  entity id, hash, filename, URI, or journal field is reachable from them.
- No notification-permission dependency, asserted by a source scan over the
  runtime modules and `_layout.tsx`.
- Media never enters JS memory whole: production registers 1 MiB-chunked file
  sources through `registerBlobSource`, and `persistInlineBlobs` — the only
  path that puts bytes in the checkpoint — is gate-only.
- Both byte-removal paths (entry asset replacement, profile-photo replacement)
  write the retained-media ledger and a completed obligation inside the same
  transaction as the delete.
- `shouldAdoptQueuedGeneration()` correctly handles the crash gap between the
  engine checkpoint and Phase-1 queue settlement, and is directly tested.
- The readiness gate is real: the engine is not constructed until
  `isNormalizedModelReady()` is true, and the launch-only backfill was replaced
  by an in-session retry timer. This satisfies the merge-blocking §12
  obligation.
