## Contract changes to the closed V7-2 surface — reviewed and accepted

The provider contract evolved in three disclosed ways, and the entire V7-2
gate matrix was re-run against the updated fake:

- `verifySnapshot(vaultId, snapshotId, expectedBytes)` returns a boolean.
  For Drive this compares the service-attested `sha256Checksum` and byte
  count of **every** exact-key candidate against the locally held candidate
  bytes, replacing V7-2's download-and-byte-compare. I verified the
  attestation chain: the cached checksum always originates from a Drive
  create/upload response or listing, `record()` cross-checks the stored
  `tb_v2_hash` property against Drive's `sha256Checksum`, and `putImmutable`
  additionally compares the response checksum against the locally computed
  hash before caching. SHA-256 + size equality over all duplicates is an
  acceptable substitute for byte download.
- `hasMedia` became `hasMediaBatch` with ≤50-name grouped queries,
  discharging the plan-v7 grouped-existence deliverable. Cache hits require
  a matching content hash, not just a name.
- `listHeads(vaultId, refresh?)`: `refresh=false` is used only by snapshot
  cleanup, which runs after the same pass already refreshed discovery.
  Cleanup deletes only snapshots present in the listing, so a stale cache
  can only cause under-deletion (leakage), never deletion of an unlisted
  object — consistent with the phase's leak-over-guess rule.

## Adapter code review

- **Token handling:** the OAuth access token appears only in the
  `Authorization` header of an in-flight request; it is never persisted,
  logged, instrumented, or embedded in state. `401` clears only the invalid
  access token via the platform abstraction and retries once.
- **Connection epoch (ADR V7-0009):** random UUID in SecureStore only,
  rotated inside both platforms' interactive `authorize()`, deleted by
  `clearGoogleTokens()`. It carries no account meaning; the SecureStore
  regression proves rotation and deletion-with-credentials. All SQLite Drive
  state is keyed by (connection epoch, vault), and the Bun/SQLite test
  proves neither another vault nor another epoch can read cached state.
- **SQLite contents:** cursors, physical file IDs, logical keys, checksums,
  sizes, validated head envelopes, retry windows, resumable-session state.
  No tokens, account labels, bodies, or journal text. Resumable session
  URIs are restart state only, validated against the exact
  `https://www.googleapis.com` origin before reuse, and never reach logs or
  evidence.
- **Immutable-create discipline:** creates are never blindly retried; an
  ambiguous response reconciles by exact key + checksum + size with bounded
  re-listing. Head updates by known physical ID are retryable and omit the
  create-only `parents` field. Downloads verify byte count and SHA-256
  against attested metadata; media downloads additionally re-hash against
  the blob hash.
- **Retry windows:** `Retry-After` persists as a durable retry-not-before
  timestamp checked before any request, so a manual sync cannot bypass it —
  regression-tested.
- **Instrumentation:** method/result classes, buckets, retry counts, and
  quota estimates only. The redaction guard (pattern scan for tokens,
  emails, session URIs, Google URLs, plus a forbidden-key scan) runs before
  every report leaves memory, and the probe writer asserts again before the
  file write and console log.
- **Fake fidelity:** the host fake is an HTTP-level Drive double that parses
  real multipart bodies and enforces the semantics learned from the live
  runs (create requires `parents`, update rejects it, change sequences,
  delayed listings, expired cursors, lost create responses). The
  real-service findings in the gate are regression-tested against it.

## Real-Drive evidence status

The Android API-36 emulator run against the disposable OAuth account stands
as implementation-agent evidence — the interactive consent flow cannot be
re-run at review from this environment. It was accepted on three grounds:

1. **Redaction verified:** the checked-in report contains no account,
   provider, URL, session, or content identifiers, and the redaction guard
   is code-enforced before write, not editorial.
2. **Internal consistency verified:** every request count reproduces from
   the reviewed code paths (import = 4 list + 1 start-token + 2 create = 7;
   fresh restore = 4 list + 1 start-token + 2 download + 1 create = 8;
   warm quiet = 2 list; one edit = 3 list + 1 download + 1 create +
   1 update = 6; 51 media hashes = 2 list), and the final cleanup count of
   8 objects equals exactly the objects the probe steps create and do not
   delete earlier: 2 surviving snapshots + 5 physical head files (4 logical
   devices, one with a deliberate duplicate) + 1 revocation marker. The
   cursor-rebuild count of 5 physical heads matches the same ledger.
3. **All measured budgets sit within the owner-approved V7-0 ceilings**,
   with retries reported separately and fault scenarios excluded from
   no-fault budgets.

The probe harness itself was reviewed: `__DEV__`-gated at both the runner
and the route, stops the v6 production runtime before the credential switch,
random probe vault, synthetic content only, cleanup in `finally`, and local
`auth.signOut()` with no global revocation endpoint anywhere in the diff.

## Findings

- **Y1 (minor — V7-4 entry obligation):** the probe-only members
  `createPhysicalHeadForProbe`, `createRevocationForProbe`,
  `deleteAllForProbe`, and `setCursorForProbe` live unguarded on the
  production `GoogleDriveSnapshotV2Provider` class; only their callers are
  `__DEV__`-gated. `deleteAllForProbe` permanently deletes every vault
  object. Harmless while the provider is unwired, but before V7-4 connects
  the provider to the production runtime these members must be removed,
  extracted to a dev-only subclass, or hard-gated so no production path can
  reach them.
- **Y2 (nit, recorded):** `initializeDiscovery` ends by calling
  `refreshDiscovery`, whose cursor-rejection recovery calls
  `initializeDiscovery` — mutual recursion with no depth bound. If Drive
  pathologically rejected every freshly issued start token, discovery would
  loop with live requests. Add a bound when next touching the adapter.
