# Owner review of Phases 1–3 — 2026-08-09

Independent review of the uncommitted Phase 1–3 implementation, run before commit.
Three parallel reviews (security/privacy, migration/data-safety, engine/protocol
conformance) plus owner verification. All four gate suites, the full Jest suite
(31 suites / 222 tests), and `bun run typecheck` pass — but passing suites test
the new machinery in isolation; the findings below are what they do not cover.

**Verdict: Phase-1 and Phase-2 gates are REOPENED. Do not start Phase 4 and do
not ship this state to users until every RELEASE-BLOCKING item is fixed and
re-verified.** The Phase-0 frozen artifacts were confirmed byte-untouched, and
the codec was differentially fuzzed against node:crypto — the protocol layer is
sound. The defects are in integration and coverage.

Confidence legend: **CONFIRMED** = reproduced by the owner-side reviewer
(executable PoC or direct code verification). **PLAUSIBLE** = reported by a
reviewer with file:line reasoning but not independently reproduced.

---

## RELEASE-BLOCKING (would harm existing users even with sync disabled)

### H1. Profile name/email/photo permanently lost if the app is killed during first-launch backfill — CONFIRMED
`src/lib/settings/store.ts:253` (partialize no longer persists profile fields;
rehydration's own `set()` immediately rewrites AsyncStorage without them) +
`src/lib/cloudSync/storage/backfill.ts:165` (profile row written only AFTER all
entry batches). Kill mid-backfill on a large journal → profile gone forever.
**Fix:** migrate the profile row first (or keep profile fields in partialize
until migration status is `complete`).

### H2. Restoring your own ZIP backup crashes the entire import — CONFIRMED
`src/lib/cloudSync/storage/repositories.ts:546`: profile-photo `mediaAssets`
insert has no `onConflictDoUpdate`; the archive carries the live `asset_id`
(and the `canReuse` branch re-inserts the existing PK). UNIQUE violation →
whole import transaction rolls back → "restore my journal" fails with nothing
imported. **Fix:** upsert (as `replaceEntryAssets` already does); skip insert
in the `canReuse` branch.

### H3. Every media deletion now leaks bytes forever — no ledger consumer exists — CONFIRMED
`syncRetainedMedia` has exactly one reference in the codebase: the insert
(`repositories.ts:165`). Entry deletion, photo removal, and avatar replacement
were all rerouted to the ledger, but no worker/reaper reads it. Privacy issue
(deleted sensitive photos persist on disk) + monotonic storage growth for all
users. **Fix (Phase-1-scoped):** minimal reaper — while no `cloud_vault` row
exists, delete bytes and mark rows immediately; full retention only once a
vault exists.

### H4. Stable-ID import: tag/prompt PK collision aborts the whole import — PLAUSIBLE
`src/lib/backupImport/portable.ts:475-489, 516-527`: dedup is by title only,
then inserts with the archive's `tag_id`/`prompt_id`. Same id under a different
local title (tag renamed since export) → PK violation → full rollback.
**Fix:** check id existence first; fall back to a fresh UUID with an id-map
entry.

### H5. Entries silently lose tag associations on import — PLAUSIBLE
`portable.ts:462-474, 585-595`: title-deduped tags register no `id:` mapping,
and per-entry resolution is either-ids-or-titles; one mapped tag suppresses the
title fallback for the rest. **Fix:** register `id:<portableId> → existingLocalId`
in the dedup path; resolve per-tag, not per-entry.

### MB-1. Sync engine: remote apply clobbers a dirty local edit whose asset is not yet publishable — CONFIRMED (PoC reproduced)
`src/lib/cloudSync/engine/inMemoryEngine.ts:171` skips only provisional
construction when assets aren't publishable; the resolve/apply path still runs,
`capturedGeneration` falls back to current (`:193`), CAS passes, remote state
overwrites the dirty entity, and the next pass publishes the remote state as
the user's edit — authored text permanently lost. Violates §4.1/§6.1.
**Fix:** when assets are unpublishable, skip the entity's apply entirely (treat
as dirty; defer whole entity), or capture generation at the deferral point.

### MB-2. `recoverTombstonedTagReferences` force-applies past the CAS — PLAUSIBLE (reviewer PoC claimed it; owner re-run showed CAS holding — must be re-examined, and the routine has confirmed adjacent defects)
`inMemoryEngine.ts:499-567`, esp. `:565`: rewrite is applied after the
CAS-guarded loop with no generation re-check. Also confirmed-by-reading: it
fires without a verified tag tombstone (incomplete ancestry should PARK per
§6.5, not recover) and picks the "prior" state by lowest hash rather than the
last pre-tombstone state. **Fix:** route the rewrite through the same CAS
check; require a verified tombstone; derive prior state deterministically from
the tombstone's ancestry.

## MERGE-BLOCKING for the sync feature (fix before Phase-2 gate re-closes / Phase 4 starts)

### MB-3. Most frozen validation caps are unenforced — CONFIRMED by inspection
`domain/validation.ts` + `ancestry/graph.ts` enforce only ~6 of the ADR-0001
cap table. Unenforced: recoveryDependencyCount, entity/device/batch-ID byte
caps, title/content/displayName/promptText/mime byte caps, tagIdsPerEntry,
assetsPerEntity, metadata depth, scalarAlternateJsonBytes, entitiesPerPass,
revocation-JSON size/formatVersion on read. A remote version with a 900 KiB
title and 10,000 tag IDs enters the domain unchallenged.

### MB-4. Phase-2 gate evidence is materially thinner than its claims — CONFIRMED by inspection
- The 34-scenario golden catalog is consumed by no Phase-2 test (only its IDs
  are checked to exist). ~16 scenarios have no engine-level exercise, including
  all four publish-crash-step fixtures, dirty-local-delete-vs-remote-edit,
  set-merge removal-wins, profile conflict, and generation-N+1's plan-required
  engine assertions.
- Two scenarios are unrepresentable today: `concurrent-destructive-actions`
  (fake provider cannot present per-device marker views) and both
  initial-seeding scenarios (`seed()` is a synchronous bulk enqueue; §8's
  checkpoint/cursor seeding is not implemented).
- "Revoked vault dominates a stale writer in every interleaving the chaos suite
  generates" — the 12 chaos seeds generate zero revocation events; revocation
  is 2 hand-written schedules × 2 kinds.
- "Reversed delivery order" affects `list()` only; the engine pulls via
  strictly-ordered `getChanges()` — versions are never delivered out of order
  to the engine in any test.
- Chaos convergence compares domain snapshots only (not graphs/heads/conflict
  records/remote object set); `authoredAt: Date.now()` breaks byte
  reproducibility; restarts don't rebuild from durable state.

### F1. Drive adapter sends the Bearer token to a URL read from SQLite without host validation — CONFIRMED by inspection
`providers/googleDrive.ts:561/:604/:650`: persisted `resumable_session_uri`
is used verbatim with `Authorization: Bearer` attached. DB tampering →
token exfiltration. **Fix:** require `https://www.googleapis.com` origin on
persisted session URIs (treat mismatch as expired session), or drop the
Authorization header on resumable PUTs (session URIs are self-authorizing).

## SHOULD-FIX (before the relevant phase ships)

- **M1** `deleteEntryInTransaction` never deletes `entry_tags`; production runs
  with `PRAGMA foreign_keys` OFF (`src/db/index.ts`) so the CASCADE never
  fires — the gate test enables FK ON and masks it. Orphans later cause
  `deleteTagInTransaction` to enqueue an `upsert` for a deleted entry
  (resurrection risk once sync ships).
- **M2** "Delete All Data" leaves `user_profile` — name/email resurrect on next
  launch via `loadProfileCache`.
- **M3** Danger-zone photo/voice wipes bypass the ledger they just populated.
- **M4** Startup hard-blocks on full backfill + reconciliation with no retry on
  error; large journals raise the H1 kill window. Render app after SQL
  migration; run backfill in background (dual-write already supports this);
  gate only sync enablement on readiness.
- **M5** Backfill/reconciliation write from row snapshots taken outside the
  transaction — stale-overwrite hazard the moment M4's fix makes it concurrent.
- **F2** `cloud_vault.account_label` column + `fetchGoogleAccountLabel`
  returning the raw email = a loaded gun; nothing writes it yet. Decide and
  record: masked label or SecureStore-only, and clear on disconnect.
- **F3** iOS refresh failure clears SecureStore tokens on ANY error including
  airplane mode → forced re-consent. Scope to `invalid_grant`/401 per ADR 0005.
- **SF-1** Recovered-tag IDs derive from the local resolved entry-version hash →
  duplicate recovered tags across devices — CONFIRMED (PoC: two live "Kindness"
  tags from one race). Derive from stable identities only.
- **SF-2** Unchanged-text candidates receive (or become) text-conflict
  primaries/recovered copies of unauthored base text.
- **SF-3** Tag/prompt rename resolution ignores the merge base (lowest-hash
  primary can demote the actual rename).
- **SF-4** A corrupt/cap-exceeding remote object aborts the whole pull pass
  instead of quarantining the entity as `degraded` (§6.3/§7.2).
- **SF-5/SF-6** Chaos-harness and in-memory-vs-SQLite divergences (edit
  sequence not injectable/persisted; generations cleared on journal-deleted;
  provisional re-verify logic absent; every pass re-publishes every known head —
  costly against real Drive; tombstone semantics unrepresented). These are the
  Phase-4 integration traps list.
- **L-series** (from the data-safety review): tag/prompt `created_at` fidelity
  loss on import; export asset ordering unstable; unhandled async onPress
  rejections in NameScreen/SettingsBottomSheet; `applyImportedProfile` fires
  three concurrent transactions (dead code — delete or serialize).

## Verified sound (do not re-litigate)

- Phase-0 frozen artifacts byte-untouched; codec delegates to the frozen
  encoder (no second implementation); incremental SHA-256 differentially
  fuzzed against node:crypto (400 random + boundary lengths) — all pass.
- Migration 0004 is genuinely schema-only; the dropped unique indexes exist on
  every install lineage; new FK tables start empty.
- Dual-write-before-backfill ordering holds across all write paths; checkpoint
  ID-stability design sound; ZIP stays backupVersion 1 with additive fields.
- Token storage is SecureStore-only (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`), backup
  rules exclude it; no revocation endpoint anywhere; no client secret; scopes
  exactly `drive.appdata openid email`; no token-bearing logs; Kotlin module
  and config plugin clean.
- Outbox generation-settle + provisional-chain rules match §4.1 and are
  unit-tested; ancestry staging/caps/cycle rejection match §5.1/§6.3;
  revocation strictest-observed-kind core logic correct; fake-provider
  contract (duplicates, collisions, pagination, idempotent delete, marker
  survival) holds.
